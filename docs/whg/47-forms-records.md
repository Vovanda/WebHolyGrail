# Формы и записи

> **Принят в работу 23.10.2026.** Решения ниже - умолчания, любое можно поменять.

Владелец сайта сам собирает в админке форму: поля, кто может её отправить, какие у
записи бывают статусы. У формы появляется своя таблица, форма на сайте и экран записей
для сотрудников. Чаще всего это внутренние объекты вроде заявок, реже - данные, которые
сайт показывает плиткой или списком.

## Где живёт

**Модуль сбоку от CMS** (R4), со своей базой и своим слоем доступа (R8). Внутри Payload
его строить нельзя по трём причинам:

- Payload узнаёт о коллекциях при запуске процесса: таблица, заведённая на ходу, без
  перезапуска не получает ни адресов API, ни экранов админки;
- Drizzle сверяет базу с конфигом: таблицу, которой нет в конфиге, в режиме push он
  удаляет, а `migrate:create` предлагает её удалить;
- CMS по замыслу заменяема ([`32-structure.md`](32-structure.md)): данные клиента не
  должны держаться на ней.

| Что                            | Где                                                       |
| ------------------------------ | --------------------------------------------------------- |
| Описание формы, проверка полей | `contracts/src/forms-records.ts`: тип и функция проверки  |
| Таблицы записей                | своя база модуля рядом с базой сайта (`/data/records.db`) |
| Создание и правка таблиц       | слой модуля, по описанию, без перезапуска                 |
| HTTP                           | `/api/records/*`; браузер - через `/internal/records/*`   |
| Конструктор и экран записей    | свой экран, встроенный в админку Payload ссылкой и видом  |

Payload убрали - модуль живёт: у него свой API, своя база и свой экран.

## Описание формы

Описание - данные по контракту, JSON (R5+).

| Часть      | Что задаёт                                                                                           |
| ---------- | ---------------------------------------------------------------------------------------------------- |
| поля       | имя, подпись, вид (текст, число, дата, выбор, флажок, почта, телефон, файл), обязательность, пределы |
| доступ     | кто отправляет, кто читает, кто правит: гость, покупатель, сотрудник                                 |
| статусы    | список состояний записи и начальное; переходы - любые, кроме обозначенных конечными                  |
| оповещения | кому письмо о новой записи                                                                           |

Имя поля даётся один раз и дальше не меняется: это имя колонки. Подпись правится
свободно.

## Таблица записи

Одна форма - одна таблица. Служебные колонки: номер, время, статус, автор (покупатель
или маркер посетителя), кто обработал.

| Правка описания   | Что делает модуль                                                      |
| ----------------- | ---------------------------------------------------------------------- |
| новое поле        | добавляет колонку                                                      |
| поле убрали       | прячет колонку; данные остаются, пока владелец не удалит их явно       |
| подпись поменяли  | только описание                                                        |
| вид поля поменяли | показывает, сколько записей не переведётся, делает копию, пересобирает |

Правка применяется под замком, по номеру версии описания. Оба цвета выкладки читают
описание из базы и видят новую версию сразу; запись, отправленную по старой версии,
слой проверяет по той версии, с которой она пришла.

## Проверка

Одна функция строит проверку из описания и работает и на сайте, и на сервере. Ошибки
возвращаются по именам полей, плохой запрос до записи не доходит. Устроено как
FluentValidation: правило на запрос, отказ до обработчика. Только здесь правило
выводится из описания формы, и писать его руками не нужно.

## На сайте

- **Блок «Форма»** рисует поля по описанию и отправляет запись.
- **Плитка и список** берут записи формы как источник. Какое поле заголовок, какое
  картинка, какое ссылка - выбирается в настройках блока.
- Каждое поле размечено `data-part="field-<имя>"`: владелец меняет вид записи своим
  CSS в «Виде блока» ([`block-appearance.md`](../ux/block-appearance.md)) - прячет поле,
  выделяет цену, красит статус.

Показ на сайте - по правилу доступа «кто читает»: записи внутренних форм гостю не
показываются вовсе.

## Экран записей

Для сотрудника: список с колонками по полям, фильтр и поиск, смена статуса, кто
обработал, выгрузка в CSV. Записи гостей - входящие сообщения: сотрудник меняет статус
и пишет заметку, текст записи не правит (так уже устроены `FormSubmissions`).

## Защита гостевых форм

Лимит отправок с адреса, предел размера тела, тип файла по содержимому (расширение
подделывается), скрытое поле против ботов. Всё это уже работает в магазине мембран и переносится оттуда.

## Что с `FormSubmissions`

Сейчас все заявки сайта лежат в одной коллекции: тип формы и данные JSON. Модуль её
не удаляет (R10): каждый тип заявки становится описанием формы, записи переносятся,
после переноса сайты переходят на блок «Форма», и только потом коллекция помечается
устаревшей.

## База

Первый диалект - SQLite, как у сайтов сейчас. Слой таблиц пишет SQL сам, по описанию,
и держит место под второй диалект: Postgres в шаблоне описан как возможный переход
(`payload.config.ts`).

## Умолчания

1. Первая форма - заявка с сайта мембран («перезвоните», «расчёт кровли»); затем
   перенос типов из FormSubmissions живых сайтов.
2. Записи пока сами по себе. Связь - поле «ссылка на запись другой формы», когда
   понадобится второй форме.
3. Выгрузка в CSV. Отправка в 1С или CRM - отдельный модуль, когда появится заказчик.

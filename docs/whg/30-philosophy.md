# Architectural rules (R0-R15)

> Правила соблюдаемые каждым разработчиком. Категория продукта, боль клиента/разработчика, что в коробке и roadmap — в [`00-overview.md`](00-overview.md). Stack rationale — в [`15-vision.md`](15-vision.md).

---

**R0. Контент живёт в базе, а не в коде.** Текст, список, баннер, ссылка - поле в Payload и чтение через `contracts/`. Нет поля, которым владелец правит это сам, - правка не принимается. Значения в коде допустимы только запасным вариантом на незаполненное поле.

**R1. Не верстать страницы голыми утилитами.** Tailwind прячется внутрь компонентов; наружу — чистый типизированный интерфейс.

**R2. Токены конечны.** Цвета / отступы / радиусы / тени — только из CSS-переменных. `bg-[#3a7bd5]` запрещён.

Шире того же правила: **оформление описывается один раз и переиспользуется.** Любое оформительское значение — цвет, тень, отступ, радиус, вид кнопки, вид карточки — живёт в общем месте (`tokens.css`, `globals.css`) и берётся оттуда по имени, а не сочиняется на месте. В этом смысл наращивания примитивов: они завязаны на палитру и настройки из админки, поэтому владелец меняет вид сайта у себя, а не через разработчика, и ничто не разъезжается. Сборка страницы становится складыванием готовых кубиков без сюрпризов. Собранный руками четвёртый вид кнопки ломает ровно это.

**R3. Изоляция фронта и бэка через контракт.** Фронт не знает бэк, граница — `contracts/`.

**R4. Масштабирование сбоку.** Новая функция = отдельный сервис / БД / модуль + фронт-секция к его API через `contracts/`. Ядро не трогается.

**R5. Секция / контрол / блок = чистая функция от пропсов, на любой глубине.** Блок не лезет в родителя, не тянет данные сам, не знает где стоит. Получает пропсы — рендерит детей.

**R5+. Блок готов к сборке мышью.** Свойства блока перекладываются в JSON: примитивы, массивы, объекты, ссылки по идентификатору. Ни обработчиков в основном наборе свойств, ни экземпляров классов, ни готовой разметки - иначе редактор не нарисует поля по описанию.

**R5++. Имя нейтральное, вид унифицированный, запас на переиспользование.** WHG — одновременно архитектурный шаблон, движок сайтов и конструктор, поэтому всё, что в него кладётся, пишется под все три роли сразу: `EntityCard`, не `DogCard`; `action-button`, не `close-video-button`. Вещь, сделанная под один сайт и под одно место, в конструктор не годится — её нельзя ни переставить, ни настроить, ни отдать следующему сайту.

**R5+++. Тема - это подмена значений палитры.** Тема переключается признаком `data-theme` у корня страницы, а не набором классов «для тёмной». Служебных цветов вроде `bg-white` и `text-gray-900` в разметке нет: только имена из палитры. Чужие компоненты при переносе переименовываются на наши имена.

**R6. Без догм.** Inline `style` — для рантайм-динамики. Utility — для скорости. Раздельный CSS — для сложных контролов. Инструмент по бусту, не по идеологии.

**R7. Целевая нагрузка на старте — нулевая.** Никакого highload авансом. Highload-готовность — следствие чистой архитектуры, добавляется по факту.

**R8. Доступ к данным инкапсулирован; конкретный слой — неважен.** К БД никто не лезет напрямую в обход слоя доступа. `api/` → репозитории. `cms/` (Payload) → его собственный слой доступа.

**R9. Абстракция следует за опытом, не предшествует ему.** Не строить обобщение раньше, чем появился конкретный опыт, который оно обобщает. Сначала одна работающая вещь — потом обобщение того, что повторилось.

**R10. Шаблон не ломает то, что уже собрано на нём.** Из шаблона ничего не исчезает молча: удалённый примитив зеркало уносит из каждого сайта, и там встаёт сборка, а забранное свойство блока хоронит вид, который владелец собрал руками в админке. Порядок обратный: сперва вещь помечается устаревшей с указанием замены, потом сайты переводятся, и только затем она уходит. То же и с настройками — новая раскладка приходит свойством рядом со старой, а не вместо неё.

**R11. Одна вещь делает одно дело.** Мера - одна причина меняться: модуль, который правят и когда меняется способ хранения, и когда меняется правило выдачи, это два модуля, слипшихся в один. Для компонентов правило звучит как «чужая забота не течёт в соседа», но нарушают его чаще на сервере - у обработчика нет вёрстки, по которой видно, что он разросся. Поэтому обработчик эндпоинта переводит запрос в вызов и обратно, а само дело живёт отдельным сценарием и проверяется без сети и базы. Правило не про длину: сто строк одного дела - нормально, тридцать строк трёх дел - нет.

**R13. Адрес сущности - человеческий, вид - в параметрах.** `/dog/zorka-veo` и `/litter/n-2026`, а не `/dog?id=123`. В параметрах адреса живёт то, что меняет показ: страница списка, выбранный вид, отбор.

**R14. Страница собирается на сервере.** По умолчанию серверный компонент с данными, полученными до отрисовки. `'use client'` - только там, где без браузера не обойтись: ввод, работа с DOM, медиа.

**R15. Из браузера - только к своему домену.** Клиентский код не ходит в CMS напрямую: адрес у неё другой, и браузер либо спросит разрешение на доступ к локальной сети, либо оборвёт запрос. Запрос идёт своим маршрутом `/internal/*`, а он уже обращается к CMS.

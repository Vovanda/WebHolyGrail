# ADR-001: SQLite по умолчанию, переезд на Postgres без полумер

**Статус:** принято
**Дата решения:** 2026-10-23
**Приоритет:** высокий
**Цена отката:** отказ от SQLite - все сайты переводятся на Postgres, установка в один шаг теряется; отказ от переезда - бизнес упирается в потолок SQLite.

## Контекст

1. Малому бизнесу нужен сайт, который ставится в один шаг, без отдельного сервера базы.
2. Растущему бизнесу нужен Postgres: параллельная запись, массивы, GIN, реплики.
3. Переезд, оставляющий в Postgres текстовые заглушки и слои совместимости, лишает его
   преимуществ Postgres.

## Решение

Мы будем держать SQLite базой по умолчанию и переводить сайт на Postgres одним скриптом.
После переезда у сайта будет только родная схема Postgres, как у сайта, жившего на нём с
первого дня. Специфика базы живёт только в адаптере хранилища; каждое поле переводится
однозначно, без логики; запись в SQLite выбирается так, чтобы вести себя как в Postgres.
Транзакции включены и на SQLite.

## Альтернативы

- Только Postgres - отрезает самых мелких: лишний контейнер и забота.
- Общая запись для обеих баз - переезд тривиален, но Postgres остаётся с полумерами.
- Только SQLite - один писатель на базу, нет массивов и GIN: потолок для роста.

## Последствия

- Хорошее: магазин тортов живёт на простой базе, рост не требует переписывания.
- Плохое: у каждого модуля два адаптера хранилища и тест на двух базах.

## Соблюдение

Запрос к базе вне адаптера хранилища и поле без однозначного перевода - блокер на ревью.

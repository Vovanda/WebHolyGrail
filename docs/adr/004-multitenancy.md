# ADR-004: Многоарендность

**Статус:** принято
**Дата решения:** 2026-10-23
**Приоритет:** высокий для сервиса и перепродажи; сайту с одним владельцем не нужна
**Цена отката:** власть платформы, выведенная из положения в дереве, - переделать все проверки доступа; тип, завязанный на глубину, - переделать роли и создание арендаторов.

## Контекст

1. Сервис и перепродажа - дерево арендаторов: платформа, партнёры, их клиенты.
2. Если власть следует из положения в дереве, перестановка узла даёт чужие права.
3. Если платформа - особый участник денег, каждую партнёрскую функцию приходится
   делать для неё второй раз.
4. Клиенты одной природы стоят на разной глубине: конечный клиент бывает прямо под
   платформой и под субпартнёром.
5. Компании сливаются и делятся.

## Решение

Мы будем:

- Хранить положение арендатора в дереве материализованным путём в версии каскада
  ([ADR-005](005-path-cascades.md)).
- Решать, какие функции у арендатора существуют и кого он может создавать, по его
  типу, а не по глубине. Конечный клиент - тупиковый тип на любом уровне: функций про
  своих клиентов у него нет, вызов через API - 403. Кто кого создаёт - матрица «тип
  родителя × тип ребёнка».
- Ограничивать глубину жёстким пределом в базе; поднять его может только платформа.
- Держать платформу и суперпользователя вне дерева: их власть - роль, а не положение.
  Если платформа ведёт тот же бизнес, у неё прокси-арендатор - обычный корень со всеми
  функциями партнёра; связь односторонняя, потеря прокси не трогает права платформы.
  Прокси служит и алиасом - одна компания под вторым брендом. Заводит прокси платформа.
- Не двигать корни, не переносить ветки между корнями и не допускать циклов - это
  проверяет база. Исключение - слияние и разделение компаний: сценарий платформы с
  подтверждением и журналом, на версиях каскадов.
- Изолировать уровни: бренд и настройки - свои или записанные прямым родителем
  ребёнку, внукам ничего не протекает. Клиент видит только прямого поставщика под его
  брендом: ни предков, ни глубины, ни пути наружу нет. Документы клиента - от имени
  прямого родителя.
- Писать в журнал каждое изменение структуры: кто, когда, что создал или перенёс.

## Альтернативы

- Платформа - корень дерева: прав платформы требует вся ветка, изоляция обрастает
  исключениями «кроме платформы».
- Платформа вне дерева без прокси: партнёрские функции дублируются для платформы.
- Тип по глубине: конечный клиент под платформой невозможен без исключений.
- Наследование значений по цепочке предков: бренд деда протекает к внуку.

## Последствия

- Хорошее: одна модель для партнёров и платформы без дублирования; перестановка узлов
  не меняет прав.
- Плохое: у платформы два лица - роль и прокси, их нельзя путать.

## Соблюдение

Права, выведенные из глубины или положения в дереве, наследование по цепочке предков и
путь в ответе API - блокер на ревью.
